2.1 Types: The Foundation of Safety

C++ is statically typed: every variable has a type fixed at compile time, and the compiler checks every use against it. This is your first and cheapest safety net — entire categories of bugs die at compile time instead of in production. The fundamental types:

TypeTypical sizeUse for
bool1 bytetrue / false
char1 byteA single byte / ASCII character
int4 bytesEveryday integers — the default
long long8 bytesBig integers
double8 bytesReal numbers — the default for floating point
float4 bytesFloating point when memory is tight (graphics, huge arrays)

The word "typical" in that table is a warning, and it is close to misleading. The standard only states minimum requirements, so the real sizes change from platform to platform. For SDK work — file formats, network protocols, public APIs — that vagueness is unacceptable. Header <cstdint> provides exact-width types:

widths.cpp 
#include <cstdint>
#include <iostream>

int main() {
    std::int32_t  file_id   = -7;          // exactly 32 bits, signed
    std::uint64_t byte_count = 9'000'000'000; // exactly 64 bits, unsigned
    //                          ^ digit separators (') aid readability

    std::cout << "id: "    << file_id
              << ", bytes: " << byte_count << "\n";
    std::cout << "int is "  << sizeof(int)    << " bytes here, "
              << "int64_t is " << sizeof(std::int64_t) << " everywhere.\n";
}

Do Use plain int and double for local, everyday arithmetic — and fixed-width types (std::int32_t, std::uint64_t) whenever the exact size matters: binary file formats, wire protocols, and the public headers of your SDK.
Why that rule is split in two

It would be simpler if one of the two kinds of type were just better. Each wins in a different place:

  • Readability. int and double in local code are short and familiar. Writing std::int32_t for every loop counter adds noise and tells the reader nothing new.
  • Speed. The standard only asks int to hold values up to 32,767, which is 16 bits. On the machines you actually ship to — x86-64 and ARM — it is 32 bits, and arithmetic on it is as fast as the hardware gets. Plain int is the type the compiler is most used to.
  • A stable public API. Your SDK header is compiled by other people, on their platform, with their compiler. long is 32 bits on 64-bit Windows and 64 bits on 64-bit Linux and macOS, so a long in your header means two different things to two clients. std::int32_t means the same thing to everyone.
  • Safe serialization. When you write bytes to a file or send them over a network, the reader on the other side counts from a fixed offset. If one field is 4 bytes on the sender and 8 on the receiver, every field after it is read from the wrong place. Here fixed-width types are not a preference — they are the only correct choice.
Type groupUse it forWhy
int, doubleLoop counters, local arithmetic, short-lived values, ordinary logicShort to read, and the natural size for the CPU
std::int32_t, std::uint64_tNetwork packets, binary files, public SDK headers, hardware registersThe same number of bits on every compiler and every platform
Common Pitfall — unsigned arithmetic Unsigned types wrap around instead of going negative: if std::uint32_t n = 0; then n - 1 is 4,294,967,295 — not −1. A classic bug is looping down to zero with an unsigned counter and never terminating. Rule of thumb: use unsigned types for bit patterns and sizes coming from the standard library, use signed types for arithmetic.

2.2 Initialization: Use Braces

Historic C++ accumulated several initialization syntaxes. Modern C++ settles on one default — brace initialization — for two reasons: it works in every context, and it refuses to narrow (silently lose information). You will meet the same thing under other names: the standard calls it list initialization, and when C++11 introduced it everybody called it uniform initialization, because one syntax finally covered every case.

braces.cpp 
#include <iostream>
#include <vector>

int main() {
    int    answer{42};              // brace init of a fundamental type
    double ratio{0.5};
    std::vector<int> primes{2, 3, 5, 7};   // works for containers too

    int truncated = 7.9;            // legal! silently becomes 7
    // int refused{7.9};            // ERROR: narrowing — compiler stops you

    int zero{};                     // empty braces = zero-initialize
    std::cout << answer << " " << ratio << " " << primes.size()
              << " " << truncated << " " << zero << "\n";
}

That commented-out line is the point: with =, assigning 7.9 to an int quietly throws away .9; with braces, it's a compile error. You just met the book's recurring theme — prefer constructs where mistakes don't compile. In other words: pick the construct that catches the error while you build, not the one that catches it while the program runs. That choice has a name — compile-time safety — and it is one of the basic habits of code other people can rely on.

That is why braces are the default, and it also tells you when the choice doesn't matter. Where nothing can narrow — a counter starting at 0, a double starting at 0.0, a copy of something that already has the right type — = is still fine, and you'll meet both forms in this book. Reach for braces whenever the two sides are different types, because that is exactly where the silent loss happens.

Common Pitfall — uninitialized variables int x; inside a function is not zero — it holds whatever bytes were already sitting in that memory, and reading it is undefined behavior. Learn that term now, because the book leans on it from here on: it means the standard sets no limit at all on what your program may do next. It may print nonsense, it may crash, or it may look perfectly correct for months and then break the day you edit an unrelated line. Notice how it differs from Day 1's undefined reference: that one is a linker error, printed on your screen, and the build stops. Undefined behavior is silent — the build succeeds and the program runs. Either initialize with a real value or use int x{};. Never declare now, initialize later "when you know the value" — declare where you know the value.
Core Guidelines ES.20: Always initialize an object · ES.23: Prefer the {}-initializer syntax

In plain words: never create a variable whose value is "whatever happened to be in that memory," and when you do initialize, prefer braces because they refuse to silently chop values down. Think of braces as a picky mover who won't cram a sofa into a car and call it "delivered":

int hits;              // BAD (ES.20): garbage value, reading it = undefined behavior
int hits2 = 0;         // OK: initialized
int hits3{};           // GOOD: zero, and braces refuse to narrow

double d = 7.9;
int a = d;             // BAD-ish (ES.23): compiles, silently becomes 7
int b{d};              // GOOD: compile ERROR — data loss must be explicit

One detail if you drop those lines into a file of your own, because the two cases are not treated alike. int refused{7.9} in braces.cpp above is a hard error in GCC and in Clang even with no warning flags at all, because 7.9 is a constant the compiler can read and measure. Here the value arrives in the variable d, which the compiler will not look inside, so GCC only warns (-Wnarrowing) and still produces a working program. Clang rejects it either way. This book compiles every sample with -Wall -Wextra -Werror — the flags Day 1 §1.5 told you to make a habit — and -Werror turns that GCC warning into an error, so on your machine the build stops.

2.3 auto: Deduce, Don't Repeat

auto asks the compiler to deduce a variable's type from its initializer. The type is still fixed and checked — auto is not "dynamic typing", it's "don't make me repeat what's already on the right-hand side":

auto_demo.cpp 
#include <iostream>
#include <string>
#include <vector>

int main() {
    auto count = 10;                 // int
    auto price = 9.99;               // double
    auto name  = std::string{"Ada"}; // std::string, stated explicitly on the right

    std::vector<std::string> team{"Ada", "Grace", "Bjarne"};

    // The best reason for auto: types that are long or nearly unwritable.
    for (auto it = team.begin(); it != team.end(); ++it) {
        //  ^ spares you: std::vector<std::string>::iterator
        std::cout << *it << " ";
    }
    std::cout << "\n" << name << " x" << count << " @ " << price << "\n";
}

Two notes on that loop. *it means "the item this iterator is pointing at" — the * unwraps the iterator to get the value, and Day 4 returns to that symbol properly when it covers pointers. And the loop is spelled out the long way here only so you can see the type name auto spared you. In real code you would write for (const auto& name : team) — the range-based for that Day 1 §1.8 used to retire exactly this boilerplate. Keep the explicit iterator for the cases that genuinely need the iterator itself, such as the position a search like std::find hands back.

Common Pitfall — auto deduces exactly what's there auto s = "hello"; makes s a const char* (a C-style pointer), not a std::string. If you want a string, say so: auto s = std::string{"hello"};. Similarly, auto drops references and const from the initializer — Day 4 returns to this when it matters for performance.
Do Use auto when the type is obvious from the right-hand side or painful to spell (iterators, lambdas). Write the type explicitly when it carries information the reader needs — especially in public SDK headers, where explicitness is documentation.
Core Guideline ES.11: Use auto to avoid redundant repetition of type names

In plain words: when the type is already written on the right side of the =, writing it again on the left adds noise and one more place to make a mistake — like signing a form twice "to be sure":

std::vector<std::string>::iterator it = team.begin();  // BAD: long, repeats info
auto it2 = team.begin();                                // GOOD: same type, zero noise

auto n = 5;            // fine: obviously int
auto x = compute();    // careful: what type is x? If a reader can't tell,
                       // spell it out — auto serves readability, not laziness

2.4 const: Your Default, Not an Afterthought

const means "this name will never be used to modify this value." The compiler enforces it. Professionals make const the default and mutability the exception, because every const is one less thing that can change behind your back — in a 50-line function, knowing that 9 of 12 variables can't change shrinks the space where a bug can hide:

const_demo.cpp 
#include <iostream>

int main() {
    const double vat_rate{0.19};       // set once, trusted everywhere after
    const int    net_cents{4'999};

    // vat_rate = 0.21;                // ERROR: assignment of read-only variable

    const int vat   = static_cast<int>(net_cents * vat_rate);
    const int gross = net_cents + vat;
    //        ^ even intermediate results: const unless they must change

    std::cout << "net "   << net_cents << "  vat " << vat
              << "  gross " << gross << " cents\n";
}

Note static_cast<int>(...): modern C++'s explicit, searchable cast. It says "I know this double-to-int conversion truncates, and I mean it" — unlike the silent narrowing from §2.2.

Core Guidelines ES.25: Declare an object const or constexpr unless you want to modify its value later on · ES.49: If you must use a cast, use a named cast

ES.25 in plain words: a variable that can't change is a variable you never have to suspect. Default to const; drop it only when the compiler complains — that complaint is the compiler telling you exactly which variables actually vary:

double rate = 0.19;        // BAD-ish: can anyone reassign this later? must check all code
const double rate2{0.19};  // GOOD: guaranteed constant; reader relaxes

ES.49 in plain words: old C-style casts like (int)x are invisible to searches and can secretly do several different dangerous things. Named casts say what you mean and are greppable:

int cents = (int)(price * 100);              // BAD: C-style cast, hides intent
int cents2 = static_cast<int>(price * 100);  // GOOD: explicit, searchable, checked

For values known at compile time, go one step further with constexpr: the compiler guarantees compile-time evaluation, and the value can be used where the language demands a constant (array sizes, template arguments):

constexpr int max_retries = 5;      // computed and frozen at compile time
constexpr double pi = 3.14159265358979323846;

Day 12 develops compile-time programming fully; for now: constexpr for compile-time constants, const for run-time ones.

2.5 References: A Second Name for an Existing Thing

A reference (T&) is an alias — another name for an object that already exists. It must be initialized when declared and can never be re-seated to refer to something else:

refs.cpp 
#include <iostream>
#include <string>

int main() {
    std::string original{"draft"};
    std::string& alias = original;   // alias IS original, under another name

    alias += " v2";                  // modifies original
    std::cout << original << "\n";   // prints: draft v2

    std::string copy = original;     // no &: an independent duplicate
    copy += " (copy)";               // original unaffected
    std::cout << original << " | " << copy << "\n";
}

References earn their keep in function parameters. Passing by value copies the argument — trivial for an int, expensive for a million-element vector. Passing by reference passes the object itself. Combining with const gives the single most common parameter style in professional C++:

params.cpp 
#include <iostream>
#include <string>
#include <vector>

// Read-only access, no copy: const T& — the workhorse.
double average(const std::vector<double>& samples) {
    if (samples.empty()) return 0.0;
    double sum = 0.0;                       // must change → not const
    for (const double s : samples) sum += s;
    return sum / static_cast<double>(samples.size());
}

// Intentional modification: T& — visible in the signature.
void append_unit(std::string& label) {
    label += " ms";
}

int main() {
    const std::vector<double> latencies{12.5, 9.8, 15.2, 11.1};
    std::cout << "avg: " << average(latencies) << "\n";

    std::string label{"p99 latency"};
    append_unit(label);
    std::cout << label << "\n";
}

Read the three options as a vocabulary of intent:

ParameterMeaningCost
T value"I take my own copy" — for small types (int, double) or when you need a copy anywayCopy
const T& value"I read yours, I won't touch it" — the default for anything bigger than a few machine wordsFree
T& value"I will modify yours" — mutation, declared honestly in the signatureFree
Core Guidelines F.16: For "in" parameters, pass cheaply-copied types by value and others by reference to const · F.17: For "in-out" parameters, pass by reference to non-const

In plain words: handing someone an int is like handing them a coin — give them a copy. Handing them a database is like handing them a warehouse — give them the address (const&), not a duplicate warehouse. And if they're supposed to renovate the warehouse, hand over the address without the "look, don't touch" sign (&):

void f(std::string s);          // BAD as read-only "in": copies the whole string
void f(const std::string& s);   // GOOD "in":  reads yours, promises not to touch
void g(std::string& s);         // GOOD "in-out": will modify yours — and says so
void h(int n);                  // GOOD: int is a coin; copying is the cheap option
Don't Don't return a reference to a local variable — the local dies when the function returns, and the reference points at a corpse (undefined behavior). A reference whose object is already gone is called a dangling reference, and you will see that term in compiler messages and in every code review. Compilers warn about the simple cases; take the warning seriously. Day 4 covers object lifetime in depth.
Core Guideline F.43: Never (directly or indirectly) return a pointer or a reference to a local object

In plain words: a local variable is a sandcastle — it exists only until the function's tide (the return) comes in. Returning a reference to it hands the caller a map to a washed-away castle:

const std::string& greet() {
    std::string s = "hello";
    return s;                 // BAD: s is destroyed right here; caller gets a dangling ref
}

std::string greet2() {
    std::string s = "hello";
    return s;                 // GOOD: return by value — the caller gets their own castle
}

The indirect version is just as fatal, and harder to spot. Returning a reference to an element inside a local container, or packing a reference to a temporary into a struct you return, is the same undefined behavior — the same bug wearing a disguise:

const std::string& first_label() {
    std::vector<std::string> labels{"p50", "p99"};
    return labels.front();    // BAD: the vector dies here, and its elements with it
}

Nothing in that function names a local variable in the return, which is exactly why it slips through. Clang does report it, but GCC 15 stays silent even at -Wall -Wextra — so here the habit has to protect you, not the compiler.

2.6 Namespaces and Scoped Enums: Names That Don't Collide

Your SDK will define names like connect, Error, Config — and so does everyone else's. Namespaces partition the world so those names can coexist:

namespaces.cpp 
#include <iostream>
#include <string>

namespace metrics {                    // your library's territory
    // Scoped enum: enumerators live inside Unit, convert to int only explicitly.
    enum class Unit { millis, seconds, minutes };

    std::string to_string(Unit u) {
        switch (u) {
            case Unit::millis:  return "ms";
            case Unit::seconds: return "s";
            case Unit::minutes: return "min";
        }
        return "?";
    }

    namespace detail {                 // convention: internals, keep out
        constexpr int version = 3;
    }
}

int main() {
    const auto unit = metrics::Unit::seconds;   // qualified access
    std::cout << "unit: " << metrics::to_string(unit)
              << " (impl v" << metrics::detail::version << ")\n";
}

Why enum class instead of the older plain enum? Two safety wins. First, the enumerators are scoped: they stay inside the enum and you name them Unit::seconds, so a Color::green and a Fruit::green can coexist. A plain enum does the opposite — it drops its enumerator names into the surrounding scope, where they collide with everything else. After enum Color { red, green }; the name green is taken, and nobody who includes your header can use it for something of their own. Second, a plain enumerator turns itself into an int, with no warning: hand red to a function that expects an int and it quietly arrives as 0. A scoped enumerator refuses. If you want the number you write static_cast<int>(Unit::seconds) and say so out loud.

You may read elsewhere that plain enums also let you compare two unrelated enums, as in red == apple. That was true for a long time, but C++20 deprecated comparison and arithmetic between two different enumeration types, so GCC and Clang now report it — and with -Werror the build fails. It is the two wins above that still do the work.

An enum class is still stored as an integer, and unless you say otherwise that integer is int — whose size can differ between platforms. Inside your own code that doesn't matter. The moment the value is written to a file or sent over a network, §2.1's rule comes back: state the exact width.

enum class Unit : std::uint8_t { millis, seconds, minutes };  // exactly 1 byte, everywhere

A scoped enum also gives you something useful in a header: you can declare it without listing its values, the way you can declare a function before you define it. This works whether or not you pinned the width, because a scoped enum always has a known underlying type — int when you say nothing:

// metrics/types.h — the real definition, with no pinned width
namespace metrics {
    enum class Unit { millis, seconds, minutes };
}

// metrics/report.h — needs the name of the type, not its values
namespace metrics {
    enum class Unit;      // compiles: a Unit is int-sized, so the compiler knows enough
    std::string format(double value, Unit u);
}

A reader of report.h learns that a Unit exists and that format takes one, and never sees the list of units. A plain enum Unit; would not compile at all, because the compiler has no idea what size to give it; you would have to write enum Unit : int; and name the type by hand.

One catch to remember: the declaration and the definition must agree on the width. If types.h pins the type with enum class Unit : std::uint8_t { … }, then report.h has to repeat it — enum class Unit : std::uint8_t;. A bare enum class Unit; would mean int, and GCC stops with "different underlying type". Day 19 uses this technique when it works out what a public header should show and what it should keep back.

Do Put everything your library exports inside one top-level namespace (Day 19 formalizes this), use a nested detail namespace for internals, and reach for enum class — never plain enum — for new code.
Core Guidelines SF.20: Use namespaces to express logical structure · Enum.3: Prefer class enums over "plain" enums

SF.20 in plain words: a namespace is a labeled drawer. Everything that belongs to your library goes in your drawer, so it can't get mixed up with anyone else's socks. Enum.3 in plain words: a plain enum puts its names into the surrounding scope, and its values behave like integers on their own. An enum class keeps its names inside the type, and its values behave like integers only when you convert them yourself:

void dim(int level);                // takes a brightness, 0-255

enum Color { red, green };          // BAD: 'red' and 'green' escape into the outer scope
// int green = 5;                   //   error: the name 'green' belongs to Color now
// dim(red);                        //   compiles silently: to the compiler, red is just 0

enum class Shade { light, dark };   // GOOD: the names stay inside Shade
int dark = 5;                       //   no clash: the enumerator is Shade::dark
// dim(Shade::dark);                //   compile ERROR: a Shade is not a number
// dim(static_cast<int>(Shade::dark));   //   fine — you asked for the number out loud

Workshop

Q&A

Q: Is auto slower than writing the type?
A: No. auto is resolved entirely at compile time; the generated machine code is identical. It affects readability, never performance.
Q: If const is so good, why isn't it the default in the language?
A: History — C++ inherited C's mutable-by-default variables and can't break decades of existing code. So professionals invert the default by habit: write const first, remove it only when the compiler proves you must.
Q: When do I pass by value vs const&?
A: Small, cheap types (int, double, bool, enums, small structs): by value. Anything that owns memory (std::string, containers, user types): const&. Day 4 adds one refinement for "I need my own copy anyway" cases.
Q: How is a reference different from a pointer?
A: A reference cannot be null, cannot be re-seated, and needs no * to use — it's a safer, stricter tool. Pointers (Day 4) remain for the cases references can't express: optional ("maybe nothing") and re-seatable relationships.

Quiz

  1. Why does int x{7.9}; fail to compile while int x = 7.9; compiles?
  2. What type does auto s = "text"; deduce?
  3. A function needs read-only access to a std::string. Write its ideal parameter declaration.
  4. Name two safety advantages of enum class over plain enum.
  5. What is wrong with std::uint32_t i = 3; while (i >= 0) { ...; --i; }?
Quiz Answers
  1. Brace initialization forbids narrowing conversions; 7.9 → int loses the fraction, so braces reject it. = permits the silent truncation to 7.
  2. const char* — a pointer to the characters of a string literal, not a std::string.
  3. void f(const std::string& s) — no copy, and the signature promises not to modify.
  4. The enumerators are scoped, so they stay inside the enum instead of leaking into the surrounding scope and taking names other code wants — you write Unit::seconds. And there is no implicit conversion to int, so an enumerator can't quietly be used as a number; when you want the number you write static_cast<int>(...).
  5. i is unsigned, so i >= 0 is always true: when i is 0, --i wraps to 4,294,967,295 and the loop never ends.

    const double scaled = total * factor;
    return scaled;
}
    The big win is const& on xs: no vector copy per call. (const on the by-value factor is optional style; it documents intent inside the function.)

Today's Project: statline — Latency Statistics

A tool that takes latency samples (milliseconds) on the command line and prints min, max, and mean — the kind of utility you'd actually write while debugging a service. It exercises everything from today: const by default, const& parameters, auto, brace init, fixed-width types, a namespace, and an enum class.

// statline — min/max/mean of latency samples given in milliseconds.
// Usage: statline 12.5 9.8 15.2 11.1
#include <cstdint>
#include <iostream>
#include <string>
#include <vector>

namespace statline {

enum class Verdict { fast, acceptable, slow };

struct Stats {
    double        min{};
    double        max{};
    double        mean{};
    std::uint32_t count{};
};

// const&: read a possibly large vector without copying it.
Stats compute(const std::vector<double>& samples) {
    Stats s{};
    s.count = static_cast<std::uint32_t>(samples.size());
    if (samples.empty()) return s;

    s.min = samples.front();
    s.max = samples.front();
    double sum = 0.0;
    for (const double v : samples) {
        if (v < s.min) s.min = v;
        if (v > s.max) s.max = v;
        sum += v;
    }
    s.mean = sum / static_cast<double>(s.count);
    return s;
}

Verdict judge(const double mean_ms) {
    if (mean_ms < 10.0)  return Verdict::fast;
    if (mean_ms < 50.0)  return Verdict::acceptable;
    return Verdict::slow;
}

std::string to_string(const Verdict v) {
    switch (v) {
        case Verdict::fast:       return "fast";
        case Verdict::acceptable: return "acceptable";
        case Verdict::slow:       return "slow";
    }
    return "?";
}

} // namespace statline

int main(int argc, char* argv[]) {
    if (argc < 2) {
        std::cerr << "usage: statline <ms> [<ms> ...]\n";
        return 1;
    }

    std::vector<double> samples;
    for (int i = 1; i < argc; ++i) {
        try {
            samples.push_back(std::stod(argv[i]));   // string → double
        } catch (const std::exception&) {
            std::cerr << "error: '" << argv[i] << "' is not a number\n";
            return 1;
        }
    }

    const auto stats = statline::compute(samples);
    std::cout << "samples: " << stats.count
              << "  min: "  << stats.min
              << "  max: "  << stats.max
              << "  mean: " << stats.mean << " ms  ("
              << statline::to_string(statline::judge(stats.mean)) << ")\n";
}
